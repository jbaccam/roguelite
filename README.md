# Copy the Scene!

This README and the root Rojo project cover Copy The Scene. The roguelite and other work in this workspace are mapped in [PROJECTS.md](PROJECTS.md).

A Roblox memory party game for 4–8 players, aimed at ages 8–16 with a middle-school sensibility. Remember a recognizable setup, rebuild it, and survive the elimination rounds. The prototype includes 20 grouped scenes across camping, skating, gaming, pizza, treasure, and expedition themes. Thirty prop definitions are available, including two adapted Creator Store props.

The stage is a coastal competition pavilion: warm wood, slate blue, soft white, and restrained amber accents. Textured cliff and tree assets surround the waterfront arena. The grid is **6×6 with four-stud cells**, reduced from 144 possible floor positions to 36. Read [ASSETS.md](ASSETS.md) for model provenance.

Players join the queue from a separate lobby with a jumping course. Four queued players start a countdown; up to eight enter in queue order. There are no bridges between match islands. All participants study one central scene through a shared camera view. After eight seconds, the camera returns to their character for free movement and building. A catapult replaces the central scene and fires a large rock at the lowest-scoring island during judging. Eliminated players can spectate or return to the lobby and queue for the next match.

## Try it in Studio

1. Open the Copy The Scene place in Roblox Studio.
2. Press **Play** (F5).
3. Click **Practice** for three solo rounds, or **Join queue** for a match with at least four queued players. The lobby's queue pad also has a join/leave prompt.
4. Memorize the central scene during the eight-second camera preview. When your camera returns to your character, rebuild the scene using the hotbar.
5. Press **DONE** twice to submit, or let the timer finish. Stop the test with **Shift+F5**.

Practice exists only in Studio and does not award saved coins or wins. Each practice round demonstrates the catapult on empty island 8; it does not eliminate the solo player. The demonstration is labeled on screen.

| Action | PC | Touch | Controller |
| --- | --- | --- | --- |
| Move / jump | WASD / Space | Roblox joystick / jump button | Left stick / A |
| Look around | Right-drag; scroll to first person | Drag / pinch | Right stick |
| Choose a prop | Hotbar or number keys | Tap hotbar; swipe to scroll | LB / RB |
| Place | Aim and click, or E | Tap a spot, then PLACE | Aim with center crosshair, RT |
| Remove | Q or REMOVE, then click the prop | REMOVE, tap the prop, then REMOVE | Aim at the prop, B |
| Submit | DONE or Enter, twice | DONE twice | X twice |

Green previews are valid; red previews explain what needs changing. Aim at the top of a stackable prop to build upward. Remove the top item first when taking a stack apart. Every prop has a fixed appearance and facing direction: there are no color, rotation, or height controls.

## Local development and source control

This folder is the Git repository connected to `jbaccam/copy-the-scene`. Luau files are the source of truth. The world and prop models are generated by code, so they are included in source control without large binary place files.

Install [Rokit](https://github.com/rojo-rbx/rokit), then run:

```powershell
rokit install
rojo build -o build/CopyTheScene.rbxlx
rojo serve
```

Open the built place to start from a clean copy, or connect Studio's [Rojo plugin](https://rojo.space/docs/v7/getting-started/installation/) to `localhost:34872` to sync the scripts into the existing place. Stop a play test before syncing, then start Play again to reload scripts and ModuleScripts. The generated map appears when Play starts; Studio MCP can also rebuild its edit preview.

GitHub stores commits and backups; Rojo handles code synchronization with Studio. Studio MCP lets Codex inspect the place, sync scripts, and exercise the game. The GitHub connector is useful for repository and workflow checks, while local Git can commit and push directly. Publishing an experience to Roblox is a separate step.

Commits use the local Git author identity. To show activity from this private repository, enable private contributions on your GitHub profile and use an email associated with your GitHub account. See [GitHub contribution settings](https://docs.github.com/en/account-and-profile/how-tos/contribution-settings).

## Project layout

| File / directory | Responsibility |
| --- | --- |
| `src/client/Main.client.luau` | Game HUD, input, camera, prop previews, spectating |
| `src/shared/Catalog.luau` | Fixed prop definitions and model construction |
| `src/shared/Placement.luau` | Grid coordinates, collision, support, automatic stacking |
| `src/shared/Config.luau` | Player limits, timings, rewards, scoring weights |
| `src/shared/Theme.luau` | Shared stage and HUD palette |
| `src/shared/AssetData.luau` | Reviewed static geometry exported from Creator Store |
| `src/server/Scenes.luau` | 20 server-only scene definitions |
| `src/server/GameService.luau` | Match phases, server validation, elimination, practice |
| `src/server/Scoring.luau` | Optimal duplicate matching and partial position scores |
| `src/server/World.luau` | Lobby, eight islands, grid tiles, scenery, effects |
| `src/server/Scenery.luau` | Static cliff and tree construction |
| `src/server/Catapult.luau` | Catapult construction, arm animation, rock trajectory |
| `src/server/Queue.luau` | Opt-in queue ordering and participant filtering |
| `src/server/Persistence.luau` | Wins / coins, retries, idempotent save receipts |
| `src/server/Tests.luau` | Engine-side rule and content checks |

Coordinates X/Z refer to the first occupied grid cell, indexed 0–5. One cell is four studs. Level is an internal support height generated by aiming at a prop. Object identity contributes 60% of the score and position contributes 40%, with partial credit for nearby placements. Matching identical props minimizes total distance rather than depending on placement order. Unmatched extra props cost five points each. Ties use previous-round totals, then a random ordering assigned once per match.

Server actions validate the player, phase, submission status, inventory, finite integer coordinates, footprint, collision, support, distance, and request rate. Target scenes stay on the server; their preview models exist on clients only during memorization. As in any visual memory game, an altered client could record the preview; server scoring prevents forged scores but cannot prevent recording what a player can see.

## Verification

```powershell
stylua --check src
rojo build -o build/CopyTheScene.rbxlx
```

During Play, run in the **server** context through Studio MCP or the server Command Bar:

```lua
print(require(game.ServerScriptService.CopyTheSceneServer.Tests).Run())
```

The engine suite checks all 20 scenes, duplicate matching, partial scores, reduced-grid boundaries, collisions, stacking support, prop footprints and ground contact, absence of executable code in prop models, and persistence merge/retry invariants. GitHub Actions checks formatting and builds a downloadable place artifact; it does not run Roblox engine tests.

Observed in Studio: free character movement and jumping; cursor placement on the intended tile; automatic stacking; rejecting removal of a supporting prop; exact builds scoring 100%; empty builds timing out; submit confirmation; practice winner and return to lobby; zero persistent practice rewards. The revised 6×6 boundary rejected removed cells, and the grouped Game Night scene scored 100% through the client submit button. Desktop and small landscape phone layouts were visually checked in Studio's emulator during development; physical-device testing is still required.

Still requiring a dedicated test session: four-to-eight simultaneous real clients, disconnect/elimination/spectator edge cases under network delay, physical phones and consoles, and published DataStore reads/writes. Studio DataStores are disabled by default. Optional Studio save testing uses a separate namespace when enabled in Config, never the production store. A failed data load pauses persistent rewards to avoid overwriting saved progress.

Cosmetic shops, final audio, and production asset polish are future work. No paid accuracy advantages are implemented.
